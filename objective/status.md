First fully successful real generation: full spec (1376×768, 124 frames, 5 steps) → `result_20260919_034559_791135.mp4`, playable H.264 video + AAC stereo audio, 5.17s, 1.2MB, **162.4s total** (1.2s load + 161.2s generation).

Getting there required fixing three real bugs surfaced only by real inference (all now in `h3.py`):
1. **Missing GPU memory lifecycle.** comfy's model manager does *not* automatically evict the Qwen encoder + video VAE before DiT inference (objective.md's memory lifecycle diagram was aspirational, not automatic) — added explicit `comfy.model_management.unload_all_models()` calls at both handoff points (Qwen/VAE → DiT, and DiT → decode VAEs). Without this the DiT couldn't fully load and denoising OOM'd on step 1.
2. **CUDA allocator fragmentation.** Even with the above fix, denoising OOM'd with `4.65 GiB reserved by PyTorch but unallocated` (PyTorch's own error message suggested the fix) — running with `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` resolved it completely. **Now wired in permanently**: `generate.py` sets it via `os.environ.setdefault(...)` as the first thing it does, before importing `h3` (and therefore before torch's CUDA allocator can initialize) — `setdefault` so an explicit shell-level override still wins. Re-verified end to end with no env var set manually: same 1376×768/124-frame/5-step generation succeeded in 165.3s, output correctly landing in `outputs/`.
3. **Missing `torch.inference_mode()` — the real root cause of a much scarier-looking bug.** After (1) and (2), full denoising succeeded at full resolution, but VAE decode OOM'd catastrophically — bisecting hands-on (varying only canvas size with a fixed tiny frame count) showed decode succeeding at 96/192/256px but failing at 320px+, which looked like a genuine upstream memory-scaling bug in ComfyUI's MiniMax H3 tiled VAE decode (researched `github.com/deepbeepmeep/Wan2GP`'s independent MiniMax H3 implementation for comparison — confirmed their decode design and ComfyUI's `decode_temporal` both correctly stream finalized chunks to CPU, ruling out that theory). Root cause: **`H3Backend.generate()` calls ComfyUI node classes directly (headless, no server/UI), bypassing `execution.py`'s `torch.inference_mode()` wrapper that comfy's real execution engine normally provides around every node call.** Without it, autograd retained the full computation graph across every op; `comfy/samplers.py` happens to wrap its own sampling loop in `no_grad()` internally (why denoising was unaffected), but VAE decode and CLIP encoding have no such internal guard and accumulated graph memory unboundedly across the multi-tile decode loop. Fix: wrapped the entire GPU-touching section of `generate()` in `with torch.inference_mode():`. One line; after this, full 1376×768/124-frame decode succeeded with room to spare — **this was never a resolution-scaling problem**, and no upstream bug or resolution compromise was needed.

Sampler defaults (`cfg=1.0`, `euler`/`simple`) produced a real, playable video — functionally validated, though visual quality/motion-adherence is not yet assessed (needs human review of the actual output).

**Output path change (2026-09-19):** `generate.py` now routes bare `--output` filenames (no directory component) into `outputs/` (auto-created), so real/mock runs no longer scatter files into the repo root. Paths with an explicit directory (e.g. tests using `tmp_path`) are respected as-is, unaffected. `outputs/` is gitignored. `make clean` now removes `outputs/` instead of a stray root-level glob.

## RunPod migration issues to consider

- **torch strategy: resolved, simpler than originally planned.** The original plan (inherit system torch via `uv venv --system-site-packages`, keep `torch` out of `pyproject.toml` entirely) is not what ended up being used. While installing ComfyUI's other deps (`torchaudio`, `torchsde`, `comfy-kitchen`, `comfy-aimdo` — needed to actually import `comfy.sd`, none of which the system image ships), `uv` pulled its own `torch` transitively to satisfy them — and it resolved a working self-contained CUDA build (`2.14.0+cu130`, bundled `nvidia-*` wheels) straight from the default PyPI index, no special `--index-url` needed. This was verified to actually work: `torch.cuda.get_device_capability()` reports `(12, 0)` (RTX 5090 Blackwell/sm_120) and a real GPU matmul ran successfully. So: modern PyPI `torch` wheels are self-contained and CUDA-enabled by default now — the old "must point at a special index or get a CPU wheel" risk no longer applies. Final setup: a `gpu` dependency-group in `pyproject.toml` (mirrors ComfyUI's `requirements.txt` essential section, UI/server-only entries dropped) — `uv sync` (no group) stays tiny/fast for `--mock`/tests, `uv sync --group gpu` pulls the full reproducible CUDA stack (~5.7GB, confirmed present in `uv.lock`). The venv also has `--system-site-packages` set (harmless fallback; not load-bearing now). `H3Backend.load()` still catches `ImportError` in addition to `cuda.is_available() == False`, so a non-GPU dev machine without the `gpu` group installed gets a clear `RuntimeError` instead of `ModuleNotFoundError`.
- **`sudo` is not present in this RunPod container** (running as root already). Fixed `make ffmpeg` to only prefix `apt-get` with `sudo` when not already root. `ffmpeg`/`ffprobe` installed via `apt-get install -y ffmpeg` and confirmed working (`test_mux_mp4_creates_playable_output` no longer skips).
- **`MODELS_ROOT` placeholder confirmed correct.** `/workspace/ComfyUI/models` — ComfyUI was git-cloned to exactly `/workspace/ComfyUI` on this instance, so the pre-existing placeholder needed no change. Created the `text_encoders/`, `vae/`, `diffusion_models/` subdirectories so `fetch_models.sh` has somewhere to write.
- **`check_disk_space()` only guards the output file** (500MB minimum), not checkpoint loading. `fetch_models.sh`'s own `check_disk_space()` (bash, separate from `h3.py`'s) already guards downloads against the real remote file size via a HEAD request — this is the download script's job, not `generate.py`'s, and it's already done (see below). 100GB total disk, 87GB free after `gpu` group install — tight if a large (~66GB) DiT variant is chosen alongside the ~21GB stock set; check `df -h` before picking a DiT.
- **The checkpoint signature check has only been validated against the official repo's own headers.** If the custom-link DiT you provide is a community fine-tune/CivitAI variant with a meaningfully different tensor layout, `validate_checkpoint()` could reject a legitimate file. If that happens, don't loosen the check blindly — inspect the real header first (same range-request trick works on CivitAI too, if it serves range requests) and adjust the signature deliberately.
- **ComfyUI-code-reuse strategy: fully verified, not just researched.** H3 support is native to core ComfyUI (`comfy_extras/nodes_minimax_h3.py`), confirmed importable headlessly (see above) and used directly (not reimplemented) in `H3Backend.generate()`.
- Confirmed `ffmpeg`/`ffprobe` present and working on this RunPod instance (installed via `apt-get`, `make ffmpeg` fixed to not require `sudo`).

## Performance research (2026-09-19): attention backend acceleration

Researched cheap, drop-in speedups for the real backend ahead of Phase 4 (no restructuring — this is about swapping in an existing ComfyUI-native optimization, not writing new inference code). Full ranked list considered: SageAttention (2 and/or 3) > ComfyUI's own `--fast` fp8/cublas flags > `torch.compile` via `comfy_api.torch_helpers.set_torch_compile_wrapper` > an NVFP4 DiT checkpoint (RTX 5090 clears the compute-capability gate for it, but no NVFP4 H3 checkpoint has been located yet) > Wan2GP-style TeaCache/step-skipping (biggest potential win, but a forward-pass patch rather than a flag — deprioritized for now).

**SageAttention2 (`sageattention` pip package):** Already natively wired into the `v0.36.0` ComfyUI checkout via a real CLI flag (`comfy/ldm/modules/attention.py`, gated on `comfy.model_management.sage_attention_enabled()` → `args.use_sage_attention`). Confirmed `h3.py`'s `_import_comfy()` never calls `comfy.options.enable_args_parsing(True)`, so `comfy.cli_args.args` always parses as `[]` (defaults) and never sees `generate.py`'s real argv — meaning it's safe to set `comfy.cli_args.args.use_sage_attention = True` directly in Python before `import comfy.sd` (the attention backend is latched at `comfy.ldm.modules.attention` import time, so the flag must be set before that import chain runs). Not yet installed or wired in. Wan2GP quotes ~30% speedup on RTX 50-series for this; it's well-tested across model families generally.

**SageAttention3 (`sageattn3` package, Blackwell/FP4-only):** Also present in this checkout (`attention3_sage` in the same file) but has **no CLI flag** for global selection — it's reachable only through ComfyUI's per-node `optimized_attention_override`/`REGISTERED_ATTENTION_FUNCTIONS` registry, which no core node exposes without a node graph. Forcing it as the global default in headless code would require monkeypatching `comfy.ldm.modules.attention.optimized_attention` (and `optimized_attention_masked`) directly, and that patch must land before `import comfy.sd`/`import nodes` (those transitively import model-definition files that bind `optimized_attention` by value at their own import time, not live). Installs from source only (`git clone https://github.com/thu-ml/SageAttention`, `cd sageattention3_blackwell && python setup.py install`; needs CUDA≥12.8/torch≥2.8, this instance has cu13.2/torch 2.14 so that's fine — confirmed no hard `python_requires` gate in `setup.py` despite the README saying "python>=3.13", though a full build wasn't completed to verify it actually compiles on this instance's Python 3.12).

**Paused, not decided:** SageAttention3's own README states it's verified lossless only for CogVideoX-2B/HunyuanVideo/Mochi/Flux/SD3.5 — **MiniMax H3 is not on that list** — and explicitly recommends a hybrid (SageAttention2++ on first/last timesteps, sage3 for the rest) for unverified models to avoid quality loss. Combined with the turbo checkpoint already running only 4-6 steps total (see Phase 3 above), applying an unverified lossy approximation across every step of an already step-starved schedule risks visible quality drift more than it would on a normal 20+ step run. Decision on full-sage3 vs. hybrid vs. sage2-only deferred to a future session — nothing implemented yet.

## Portability fix: COMFYUI_ROOT default (2026-09-19)

`COMFYUI_ROOT` (and therefore `MODELS_ROOT`, `make comfyui`'s clone target) was hardcoded to the RunPod-specific `/workspace/ComfyUI` in both the `Makefile` and `h3.py`, with no relation between them beyond both authors happening to type the same string — confirmed broken on GitHub Codespaces, where the analogous mount is `/workspaces/` (plural). Fixed in both places to derive the same sibling-directory default instead of hardcoding either spelling:

- `h3.py`: `COMFYUI_ROOT = os.environ.get("COMFYUI_ROOT", str(Path(__file__).resolve().parent.parent / "ComfyUI"))` — same sibling-directory rule, resolved from this file's own location rather than CWD so it's correct regardless of where `generate.py` is invoked from (the Makefile always runs from the repo root, but a direct `uv run python generate.py` invocation might not).

Verified hands-on on this Codespaces instance: `make -n comfyui` and `python3 -c "import h3; print(h3.COMFYUI_ROOT)"` both resolve to `/workspaces/ComfyUI` (this repo is at `/workspaces/videomodeltests`), and `make comfyui` successfully cloned there. The `COMFYUI_ROOT`/`MODELS_ROOT` env var override (documented in the README's "Configuration" section) is unaffected — this only changes the fallback when neither is set. `MODELS_ROOT` placeholder note above (`/workspace/ComfyUI/models`, confirmed correct on the RunPod instance) still stands as a historical record of that specific instance; it's no longer the literal default in code.

## Fast downloads: hf-xet high-performance mode (2026-09-21)

Researched the modern equivalent of the old `HF_HUB_ENABLE_HF_TRANSFER=1` flag: `hf_transfer` is deprecated/removed now that the Hub is fully on Xet storage, and current `huggingface_hub`/`hf` already uses the Rust-based `hf-xet` backend by default *if the `hf_xet` extra is installed* — otherwise it silently falls back to plain HTTP with a one-line warning. `fetch_models.sh`'s `hf()` wrapper previously ran `uvx --from huggingface_hub hf`, i.e. without the extra, so every download was hitting that slow-path fallback.

Fixed: `hf()` now runs `uvx --from 'huggingface_hub[hf_xet]' hf`. Also wired up `HF_XET_HIGH_PERFORMANCE` (a real upstream env var that saturates network+CPU for large transfers, but the docs call for ~64GB+ RAM to safely buffer at that rate) — auto-enabled only when `/proc/meminfo` reports that much RAM (true on the ~92GB RunPod target, false on this ~8GB dev box — verified both the detection logic and the `usage()`/`resolve_models_root()` messaging by hand on this dev box), always overridable by an explicit env var or `.env` entry (same precedence convention as `HF_TOKEN`). Documented in the README's new "Fast downloads (hf-xet)" section. Not yet verified against a real multi-GB download on RunPod (this dev machine can't run one) — worth confirming the speedup is real on the next RunPod session.

## Docker image for a RunPod template (2026-09-21)

Added `Dockerfile`, `.dockerignore`, `scripts/docker-entrypoint.sh` so this repo can be built into a RunPod template image. Design decisions, settled with the user before implementing:

- **No `nvidia/cuda` base image.** `python:3.12-slim-bookworm` for both build/runtime stages — the `gpu` group's torch wheel already bundles its own CUDA runtime (confirmed on this RunPod target's `cu130`/torch 2.14 build earlier in this doc), and RunPod's container runtime injects the host driver (`libcuda.so.1` etc.) into any base image. Revisit only if something needs `nvcc`/the CUDA toolkit at build or run time (e.g. the paused SageAttention3 source build).
- **Multi-stage build.** `builder` stage: `git`, clones the pinned ComfyUI ref (`.git` stripped after clone), `uv sync --frozen --no-dev --group gpu` into `/opt/venv` (`UV_PROJECT_ENVIRONMENT=/opt/venv`). `runtime` stage: only `ffmpeg`/`curl`/`bash`/`ca-certificates` + the venv + the ComfyUI checkout copied in — no git, no build tools, no dev dependencies (pytest/ruff dropped via `--no-dev`). `tests/`/`objective/` excluded from the image via `.dockerignore` — not needed at runtime.
- **No persistent volume, deliberately — the user's explicit call**, overriding an earlier draft of this plan that recommended a RunPod Network Volume for `MODELS_ROOT`. The user is fine paying a full model re-download (stock ~21GB + a DiT checkpoint) on every fresh container start in exchange for not paying for/managing a volume. `MODELS_ROOT` is left at its default (`$COMFYUI_ROOT/models`, `COMFYUI_ROOT=/ComfyUI` set explicitly in the image) — no env override baked in. README now calls out that RunPod's Container Disk size needs to be set well above image size + ~90GB, since there's no separate volume to absorb that.
- **Entrypoint (`scripts/docker-entrypoint.sh`), not tmux**, per the user's own instinct and this session's reasoning: `exec`'s into the real process (Flask server, or `check`/`bash` for debugging) so it's PID 1, gets `docker logs`/signal handling for free, and doesn't need tmux's session-survival trick since Docker's container lifecycle already provides that. Sequence: `fetch_models.sh stock` (always — idempotent via `hf download`'s own etag check, but genuinely re-downloads here since there's no volume to make that idempotency pay off across restarts) → `fetch_models.sh dit "$DIT_URL"` only if `DIT_URL` is set (a missing DiT is non-fatal — `web/server.py`'s `_init_backend()` already catches `discover_dit_checkpoint()` raising and surfaces it as `backend_error` via `/api/status` instead of crashing, confirmed by reading that code path, not assumed) → `exec` into `serve` (default `CMD`) / `serve-mock` / `check` / `bash`.
- **Pre-warmed `uvx` tool cache for `hf`** (`uvx --from 'huggingface_hub[hf_xet]' hf --version` as a `RUN` step) so the entrypoint's first real `fetch_models.sh` call at container start pays only for the actual model download, not also for installing `huggingface_hub[hf_xet]` fresh into an ephemeral `uvx` env every single time.
